# Patch v3

Goal: add Discord-native interaction and presentation after v2 tool calling works: components, bot actions, modals, richer receipts, and interactive questions.

V3 promotes the main interaction items deliberately deferred from v0/v1/v2: components, modals, ask-question actions, and richer bot-rendered output.

## V3 scope

Possible features:

- Structured bot actions.
- Discord Message Components.
- Buttons, selects, modals.
- Component-based citations/receipts.
- `discord.ask_question` action.
- `Ask about this...` context menu modal.
- Built-in non-AI bot commands callable by Patch through typed actions.
- Optional richer rendering for summaries/search results without turning every Patch message into a component panel.

## Structured bot actions

Structured bot actions are not data-fetching tools in the usual sense. They are commands built into the bot that let Patch ask the harness to render richer Discord output.

Examples:

- create an embed
- create a poll-like button row
- ask a user a question with buttons
- open a modal
- show compact search result cards or citations/receipts after a web-backed answer
- render a quoted/contextual answer block
- invoke a built-in non-AI bot command

Internal shape:

```ts
type BotAction = {
  name: string;
  arguments: Record<string, unknown>;
  visibility?: "public" | "ephemeral";
};
```

Transport depends on backend capability:

1. Native tool-call backends expose bot actions as additional typed tools, such as `discord.render_embed`, `discord.ask_question`, or `patch.run_command`.
2. Fallback backends use a separate tagged protocol such as `<bot_action>...</bot_action>` rather than overloading final Markdown.

## Constraints

- Arbitrary extra model output channels are usually not available unless the API/runtime supports them.
- The harness can still distinguish internally between `final_response`, `tool_call`, and `bot_action`.
- In native mode, data tools and bot actions may travel through the same API-level tool-call mechanism, then be routed differently by the harness.
- In fallback mode, bot actions need an explicit text protocol and parser.
- Bot actions must use strict schemas.
- Patch should not emit raw Discord component JSON directly unless the schema intentionally allows it.
- Bot actions should appear only when contextually useful.
- Do not attach generic button/reaction dumps to every Patch message.
- Patch must not edit thread/forum titles as a bot action.

## ask_question

`discord.ask_question` lets Patch post a response in the form of a question with predefined component options.

Rules:

- It may render buttons/selects.
- Users must also be able to answer naturally by replying with arbitrary text.
- It should feel like Patch asking a question, not like a bot form unless formality is useful.

## Ask about this...

Reserved message context menu command:

- `Ask about this...`

Expected behavior:

1. User right-clicks a message.
2. Patch opens a modal asking what the user wants Patch to do with the selected message.
3. Patch reconstructs context from the selected message upward.
4. Patch answers as a normal reply.

This is deferred until modal UX is worth implementing.

## Component receipts

After v2 web search/fetch works with Markdown citations, v3 can render receipts as components or compact source cards.

Important: receipts are driven by turn state from actual tool calls, not by model text.

## Multi-target responses

V3+ may add a structured response action that lets Patch send separate replies to different Discord message IDs when neighboring context needs separate responses.

This requires a structured response protocol or bot-action channel for selecting reply targets.

V0/v1/v2 always reply to the triggering message.
