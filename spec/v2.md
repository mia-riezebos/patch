# Patch v2

Goal: add controlled tool use, web search/fetch, citations/receipts, user-owned interaction preferences, and reserved future compaction commands after the v1 Discord-only harness is stable. V2 still avoids rich Discord components unless explicitly promoted from v3.

V2 promotes the main items deliberately deferred from v0/v1: tool calling, web-backed answers, and user-owned preference prompts.

## V2 scope

Implement candidates:

- Native/API-level tool-call support where reliable.
- Tagged text fallback tool protocol for local/open models.
- `web_search` and `web_fetch`.
- Markdown citations/receipts for web-backed answers.
- Short-lived per-turn state for tools and receipts.
- User-owned interaction preferences.
- Preference validation with rule-based and model-based checks.
- Reserved `/compact` command name, but no compaction behavior until UX is designed.

Do not implement yet unless deliberately pulled forward:

- Discord Message Components for citations.
- Buttons/selects/modals.
- `ask_question` components.
- Multi-target replies.
- In-flight rewrite/cancellation.
- Actual compaction UX beyond reserving command names.

## Tool use

Tool calls are internal and must never be sent to Discord.

Initial tools:

- `web_search`
- `web_fetch`

Normalize all tool calls internally:

```ts
type ToolCall = {
  name: string;
  arguments: Record<string, unknown>;
};
```

Support two transports:

1. **Native/API-level tool channel**, for backends that support OpenAI-style `tools` / `tool_calls`, Anthropic-style typed tool blocks, or equivalent structured output.
2. **Tagged text fallback**, for local/open models that do not reliably support native tool calls.

The prompt must be capability-aware:

- Native mode: provide tools through API/tool schema; do not mention tagged text protocol.
- Tagged fallback mode: include tool descriptions and tagged protocol instructions in the prompt.

Tagged fallback format:

```xml
<tool_call>
{"name":"web_search","arguments":{"query":"llama.cpp OpenAI compatible server API"}}
</tool_call>
```

Tagged fallback result:

```xml
<tool_result name="web_search">
...
</tool_result>
```

Native tool-call backends use the backend's native tool-result format.

## Tool loop

1. Send the prompt to the model.
2. In native mode, provide tools through the backend's tool schema.
3. In tagged fallback mode, include tool protocol instructions.
4. Execute returned tool calls.
5. Append tool results to model context.
6. Repeat until final Markdown response or `MAX_TOOL_CALLS`.
7. Never post tool calls/results directly to Discord.

Recommended env:

```env
LLM_TOOL_MODE=auto # auto | native | tagged | off
MAX_TOOL_CALLS=3
```

## Web fetch safety

For `web_fetch`:

- Reject non-HTTPS URLs.
- Reject raw IP-address hosts; only hostnames are accepted.
- Resolve hostnames and reject private, loopback, link-local, multicast, and otherwise non-public IP ranges after DNS and after redirects.
- Reject redirects to disallowed schemes, IP literals, or private/non-public ranges.
- Reject non-HTML MIME types.
- Enforce response size and timeout limits.

## Citations / receipts

If `web_search` or `web_fetch` is invoked in a turn, receipts/sources must be included with the final response.

V2 starts with compact Markdown citations/receipts. Later component-based receipts can replace or augment them.

The harness must not rely on the model to remember to include receipts. Use turn state from actual tool calls.

## Turn state

The harness should maintain short-lived per-turn state while generating a response. This is not conversation memory; it tracks execution facts the harness must not rely on the model to restate perfectly.

```ts
type TurnState = {
  toolCalls: ToolCallRecord[];
  botActions: BotActionRecord[];
  sources: SourceRecord[];
  shouldRenderReceipts: boolean;
};
```

Use cases:

- Track actual web searches/fetches.
- Render required Markdown receipts.
- Track future bot actions/components that need to be appended.

This can be in memory for a single turn. If interaction components later need to survive process restarts, store minimal component/action metadata, not conversation transcripts.

## User-owned interaction preferences

Patch may store user-owned preference prompts in a local database. This does not violate the no-conversation-store rule as long as actual conversation transcripts remain in Discord only.

Preferences are global per Discord user, not per guild.

Purpose:

- Let users define how they want Patch to interact with them.
- Let users opt into custom tone, verbosity, boundaries, accessibility preferences, or recurring context about their preferences.
- Append these preferences when that user is the message author or explicit target of the interaction.

Commands:

- `/preferences set text:<prompt>`
- `/preferences show`
- `/preferences clear`

Planner/final prompt behavior:

- The planner should see relevant user preferences.
- The final response prompt should receive applicable preference text verbatim as low-priority user-owned context.
- Preference text should be combined with planner vibe/style guidance.
- Preferences must never override Patch's core system prompt or harness safety rules.

Validation before storage:

Use both rule-based and model-based checks.

Reject or rewrite preferences that attempt to:

- override Patch's core system prompt or developer rules
- grant tool permissions
- force Patch to ignore other users' boundaries
- impersonate other users
- exfiltrate hidden prompts or internal state
- make Patch always respond in threads
- disable safety or leave behavior
- allow forbidden mentions

Stored preferences are lower-priority user context, not system authority.

## Commands

V2 tool commands:

- `/search query:<text>` — forces web search, then answers.
- `/find url:<url> question:<text>` — fetches a URL and answers using it.

V2 preference commands:

- `/preferences set text:<prompt>`
- `/preferences show`
- `/preferences clear`

Reserved for later:

- `/compact message:<url-or-id optional>` — reserved for future compaction behavior; do not implement until compaction UX is designed.

## LLM client v2 additions

V2 tool-capable clients can extend the v0/v1 boundary with:

```ts
type ToolDefinition = {
  name: string;
  description: string;
  inputSchema: unknown;
};

type ToolAwareLlmRequest = LlmRequest & {
  tools?: ToolDefinition[];
  toolMode: "native" | "tagged" | "off";
};

type ToolAwareLlmResponse = LlmResponse & {
  toolCalls: ToolCall[];
};
```

Streaming remains optional and should not drive Discord partial edits in v2.
